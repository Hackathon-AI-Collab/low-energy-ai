
* Low-Energy AI (LEAI) Platform

** 1. Vision & Mission

*Vision:* To create a decentralized, resilient, and low-power AI platform that delivers critical knowledge and communication capabilities to individuals in the world's most challenging environments, including disaster zones and conflict areas.

*Mission:* To build a mobile-first application using *Expo* that runs an offline-capable Large Language Model (LLM) augmented by a dynamic, peer-to-peer synchronized knowledge base. The system will prioritize low power consumption, a minimal detection signature (via BLE), and operational effectiveness in disconnected settings.

-----

** 2. Core Use Cases

*** Primary (Information Retrieval)
1.  *Field Medicine & Triage:* Provide immediate, authoritative medical guidance (e.g., TCCC) to medics and first responders.
2.  *Search & Rescue:* Offer checklists and procedural guidance for complex operations like collapsed structure assessment.
3.  *Technical Information:* Act as an interactive manual for equipment, pharmaceuticals, and other technical domains.
4.  *Emergency Communication:* Encrypted messaging between team members with offline delivery.
5.  *Situational Awareness:* Location-based information retrieval and offline mapping integration.

*** Secondary (System & Network)
6.  *Peer-to-Peer Knowledge Sync:* Automatically distribute updated knowledge base documents (e.g., new medical protocols) to nearby devices over BLE.
7.  *Low-Signature Communication:* Use BLE for communication to reduce the risk of detection compared to Wi-Fi or cellular.
8.  *Mesh Network Resilience:* Devices relay updates through intermediate nodes, creating redundant communication paths.

-----

** 3. System Architecture

The LEAI platform is designed as a modular application using the Expo framework. The architecture is broken down into four main layers: the *Application Layer*, the *Core Logic Layer*, the *Data & Sync Layer*, and the *Security Layer*.

LEAI Architecture Diagram

*** 3.1. Application Layer (UI/UX)

- *Framework:* Expo (React Native)
- *Runtime & Bundler:* Bun
- *Language:* TypeScript
- *UI Components:* A simple, clean, and intuitive chat-based interface.
  - =ChatScreen=: The main interface for querying the LLM.
  - =KnowledgeBaseScreen=: Allows users to view and manage the documents in their local knowledge base.
  - =SyncScreen=: Provides status on P2P synchronization and connected peers.
  - =SettingsScreen=: For app configuration.
  - =NetworkScreen=: Shows mesh network topology and device health.
- *State Management:* Zustand for global state management, including LLM status, sync progress, and user settings.

*** 3.2. Core Logic Layer (The "Brain")

This layer is responsible for processing user queries and generating responses. It operates entirely offline.

- *LLM Engine:*
  - *Model:* A small, highly quantized, instruction-tuned model (e.g., =Phi-3-mini=, =Llama-3.1-8B=) converted to ONNX format for mobile optimization.
  - *Runtime:* =onnxruntime-react-native= for native ONNX model inference with GPU acceleration support.
  - *Fallback:* Cloud-based inference with local caching for critical queries when local model is unavailable.
- *RAG (Retrieval-Augmented Generation) Pipeline:*
  1.  *User Query:* A user asks a question in the =ChatScreen=.
  2.  *Embedding Generation:* The query is converted into a vector embedding using a lightweight, on-device sentence-transformer model.
  3.  *Vector Search:* The query embedding is used to perform a similarity search against the *Vector Store*.
  4.  *Context Retrieval:* The most relevant text chunks from the knowledge base are retrieved.
  5.  *Prompt Augmentation:* The retrieved text chunks are combined with the original user query into a single, context-rich prompt.
  6.  *LLM Inference:* The augmented prompt is sent to the LLM Engine, which generates a final, context-aware answer.
  7.  *Response:* The answer is streamed back to the UI.

*** 3.3. Data & Sync Layer

This layer manages the distributed knowledge base and handles peer-to-peer synchronization with conflict resolution.

- *Knowledge Base:*
  - *Storage:* Source documents (PDFs, Markdown files, etc.) are stored on the device's local filesystem using *=expo-file-system*=
  - *Document Processing:* When a new document is added, it is parsed, chunked into smaller, manageable pieces, and converted into embeddings.
  - *Document Lifecycle:* Implement document importance scoring, expiration dates, and archival for old protocols.
- *Vector Store:*
  - *Technology:* Hybrid approach using SQLite for metadata and FAISS compiled to WASM for vector operations.
  - *Optimization:* Implement document chunking with overlap to maintain context across boundaries.
- *Distributed Knowledge Management:*
  - *Version Control:* Vector clocks for distributed versioning to handle concurrent updates.
  - *Conflict Resolution:* Intelligent merging of concurrent document updates with user notification of conflicts.
  - *Delta Synchronization:* Only transfer document chunks that have changed to minimize bandwidth usage.
  - *Priority-based Sync:* Critical medical protocols sync first, reference materials second.
- *P2P Synchronization:*
  - *Protocol:* Bluetooth Low Energy (BLE) with mesh networking capabilities.
  - *Library:* =react-native-ble-plx= (requires a custom development client).
  - *Mechanism:*
    1.  *Service & Characteristic:* A custom BLE service will be defined for LEAI. It will have characteristics for:
        - =KNOWLEDGE_BASE_VERSION=: A hash or timestamp of the current knowledge base.
        - =DOCUMENT_TRANSFER=: For sending and receiving document chunks.
        - =NETWORK_TOPOLOGY=: For mesh network routing information.
        - =DEVICE_HEALTH=: Battery level, storage space, sync frequency.
    2.  *Advertising & Scanning:* Devices will advertise their =KNOWLEDGE_BASE_VERSION= and device health. In the background, the app will scan for other LEAI devices.
    3.  *Sync Trigger:* When a device detects a peer with newer documents, it will initiate a connection.
    4.  *Data Transfer:* The requesting device will ask for specific document chunks. Documents will be compressed, encrypted, and sent over the =DOCUMENT_TRANSFER= characteristic.
    5.  *Mesh Routing:* Devices can relay updates through intermediate nodes to reach devices outside direct BLE range.
    6.  *Integration:* Once received, new documents are verified, processed, and integrated into the local RAG pipeline.

*** 3.4. Security Layer

This layer ensures data integrity, confidentiality, and authenticity across the distributed network.

- *Cryptographic Security:*
  - *Document Integrity:* SHA-256 hashes for document authenticity verification.
  - *End-to-End Encryption:* AES-256 encryption for all BLE communications.
  - *Key Management:* Device-specific keys with optional passphrase protection.
- *Access Control:*
  - *Document Permissions:* Role-based access to sensitive medical protocols.
  - *Audit Trail:* Logging of document access and modifications.
- *Operational Security:*
  - *Low-Signature Operation:* Minimal BLE advertising to reduce detection risk.
  - *Data Sanitization:* Automatic removal of sensitive metadata during sync.

** 5. Risk Mitigation & Contingencies

*** Technical Risks
- *Mobile LLM Performance:* Prototype with smaller models first, implement cloud fallback.
- *BLE Range Limitations:* Test in various environmental conditions, implement mesh networking.
- *Storage Constraints:* Implement document lifecycle management and compression.
- *Battery Drain:* Optimize sync frequency and implement intelligent power management.

*** Operational Risks
- *Network Fragmentation:* Implement robust conflict resolution and eventual consistency.
- *Data Corruption:* Add multiple layers of integrity checking and automatic recovery.
- *User Training:* Create intuitive interface and comprehensive documentation.

*** Security Risks
- *Detection:* Minimize BLE signature and implement operational security measures.
- *Data Breach:* Use strong encryption and implement access controls.
- *Supply Chain:* Verify all dependencies and implement integrity checking.
